## Executive Summary

## Required Changes

### 1. Task-3: Comments Support

**Priority:** High
**UI Status:** Ready to implement once backend supports it

#### What the UI Needs

The UI wants to add/edit/delete comments on issues. We need the PATCH endpoint to support updating the `properties.comments` array.

#### Proposed Comment Structure

```json
{
  "properties": {
    "comments": [
      {
        "id": "uuid-string",
        "author": "human",
        "text": "This is a comment with **markdown** support",
        "created_at": 1738368000000,
        "updated_at": 1738368000000
      }
    ]
  }
}
```

#### Questions for Backend

1. **Does PATCH already support nested property updates?**
   - Can we do `PATCH /nodes/api/nodes/{label}` with body `{ "properties": { "comments": [...] } }`?
   - Or does it replace the entire properties object?

2. **Should comments have a dedicated API?**
   - Alternative: `POST /nodes/api/nodes/{label}/comments`
   - Would provide better validation and atomic operations

3. **ID Generation:**
   - Can the UI generate UUIDs client-side (`crypto.randomUUID()`)?
   - Or should the backend generate IDs?

#### UI Implementation Plan (Once Backend Ready)

```javascript
// Add comment
async addComment(nodeLabel, commentText) {
    const node = await this.graphService.getNode(nodeLabel);
    const comments = node.properties?.comments || [];
    comments.push({
        id: crypto.randomUUID(),
        author: 'human',
        text: commentText,
        created_at: Date.now()
    });
    await this.graphService.updateNode(nodeLabel, {
        properties: { ...node.properties, comments }
    });
}
```

### 2. Task-8: Graph Data Fetching API

**Priority:** Medium (blocks graph visualization feature)
**UI Status:** Can build visualization component with mock data, but needs real endpoint

#### What the UI Needs

An endpoint to fetch a node with its connected nodes for graph visualization.

#### Proposed Endpoint

```
GET /nodes/api/nodes/{label}/graph?depth=N
```

Where `depth` is the number of link hops to traverse (default: 1).

#### Expected Response Structure

```json
{
  "root": "Bug-1",
  "nodes": [
    {
      "label": "Bug-1",
      "title": "Fix login issue",
      "node_type": "bug",
      "status": "in-progress",
      "properties": { ... }
    },
    {
      "label": "Feature-3",
      "title": "User Authentication",
      "node_type": "feature",
      "status": "done",
      "properties": { ... }
    },
    {
      "label": "Task-5",
      "title": "Add OAuth support",
      "node_type": "task",
      "status": "todo",
      "properties": { ... }
    }
  ],
  "links": [
    {
      "source": "Bug-1",
      "target": "Feature-3",
      "link_type": "relates-to"
    },
    {
      "source": "Feature-3",
      "target": "Task-5",
      "link_type": "has-task"
    }
  ]
}
```

#### Use Cases

1. **Single node view (depth=1):** Show immediate connections
2. **Feature exploration (depth=2):** Show feature -> tasks -> bugs
3. **Full project graph (depth=N or special endpoint):** Visualize entire project

#### Alternative Approaches

If a dedicated endpoint is complex, we could:
1. Use existing `GET /nodes/api/nodes` and `GET /nodes/api/links` separately
2. Have the UI do the traversal client-side (less efficient but works)

### 3. Task-9/10/11: New Node Types

**Priority:** High (part of Feature-13: Schema Extensions)
**UI Status:** UI can display new types once backend accepts them

#### New Node Types Needed

| Type | Purpose | Suggested Statuses |
|------|---------|-------------------|
| `version` | Release milestone | planned, in-progress, released |
| `user-story` | User need/scenario | draft, ready, implemented, validated |
| `person` | Team member/assignee | active, inactive |

#### Configuration Files to Update

**`.issues/config/node-types.json`** (or equivalent):

```json
{
  "version": {
    "color": "#f59e0b",
    "icon": "milestone",
    "statuses": ["planned", "in-progress", "released"],
    "default_status": "planned"
  },
  "user-story": {
    "color": "#06b6d4",
    "icon": "document",
    "statuses": ["draft", "ready", "implemented", "validated"],
    "default_status": "draft"
  },
  "person": {
    "color": "#8b5cf6",
    "icon": "user",
    "statuses": ["active", "inactive"],
    "default_status": "active"
  }
}
```

#### New Link Types Needed

**`.issues/config/link-types.json`** (or equivalent):

```json

  "has-feature": {

  },

    "inverse": "has-task",

  "has-story": {
    "inverse": "story-of",
    "description": "Version/Feature has this user story"
```

## Current API Endpoints Reference

Based on what the UI currently uses:

| Method | Endpoint | Purpose |
|--------|----------|---------|
| GET | `/nodes/api/nodes` | List all nodes |
| GET | `/nodes/api/nodes/{label}` | Get single node |
| POST | `/nodes/api/nodes` | Create node |
| PATCH | `/nodes/api/nodes/{label}` | Update node |
| DELETE | `/nodes/api/nodes/{label}` | Delete node |
| GET | `/nodes/api/links` | List all links |
